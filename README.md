# LLM Code Bench

Открытый бенчмарк для оценки больших языковых моделей в задачах
**анализа существующего кода** (code-to-code), а не только генерации с нуля.

Курсовая работа, 1 семестр. Тема: «Разработка комплексного бенчмарка
для оценки качества LLM в задачах анализа программного обеспечения».

## Зачем это нужно

Существующие бенчмарки (HumanEval, MBPP) проверяют только `text -> code`:
модель пишет функцию по её описанию. В реальной разработке важнее другое:
починить чужой баг, отрефакторить легаси, объяснить алгоритм, оценить
влияние правки на соседние модули. Мы собираем датасет и стенд именно для
таких задач.

## Модули задач

| ID | Название | Вход | Метрика |
|----|----------|------|---------|
| T1 | Lint / static-analysis fix | код с синтаксической ошибкой или warning | Exact Match фикса, Accuracy типа ошибки |
| T2 | Security bug detection | код с известной уязвимостью (CWE) | Precision/Recall строк, F1 по CWE |
| T3 | Refactoring | легаси-код | unit-тесты + снижение сложности |
| T4 | Impact analysis | монорепо + запрос на изменение | Recall покрытия графа вызовов |
| T5 | Algorithm explanation | оптимизированный код без комментариев | BERTScore / ROUGE-L против эталона |

Сейчас реализованы **T1, T2 и T3**: у каждого свой датасет, промпт, парсер
ответа и метрики, все прогоняются одним скриптом. T4–T5 добавляются по
роадмапу.

## Пайплайн

```
data source -> jsonl dataset -> harness (LLM client) -> evaluator -> leaderboard
```

Все LLM (GigaChat, OpenAI, локальные) прячутся за общим интерфейсом
`LLMClient`. Промпты стандартизированы, чтобы условия были равными.
Код, который пишет модель (T3), запускается только в изолированной
Docker-песочнице (`src/sandbox.py`).

## Быстрый старт

```bash
pip install -r requirements.txt
python -m scripts.run_demo
```

Скрипт прогонит T1 (41 кейс), T2 (23 кейса) и T3 (31 кейс) через
реальную модель GigaChat + два калиброванных baseline'а и напечатает
лидерборд — отдельную таблицу на каждый таск.

Для T3 нужен запущенный **Docker Desktop**: при первом запуске скрипт сам
скачает образ `python:3.12-slim` (около 180 МБ). Если Docker не запущен, T3
пропускается с понятным сообщением, а T1 и T2 считаются как обычно — код
модели вне контейнера не запускается никогда. Результаты сохранятся
в папку `results/`.

Для работы GigaChat нужен ключ. Создай файл `.env` в корне проекта:

```
GIGACHAT_CREDENTIALS=твой_Authorization_key
```

Ключ выдаётся на https://developers.sber.ru/studio на бесплатном тарифе Freemium.
Файл `.env` **не** коммитится в git — он в `.gitignore`.

Ключа нет — ничего не надо комментировать: `run_demo` собирает список
моделей по переменным окружения и без ключей крутится на baseline'ах, без сети.

### Добавить ещё модель

Править код не нужно, достаточно дописать переменные в `.env`:

```
GIGACHAT_CREDENTIALS=...            # GigaChat (GIGACHAT_MODEL — какая именно)
OPENAI_API_KEY=...                  # OpenAI (OPENAI_MODEL, напр. gpt-4o-mini)
LOCAL_LLM_BASE_URL=http://localhost:11434/v1   # Ollama / llama.cpp / vLLM / LM Studio
LOCAL_LLM_MODEL=qwen2.5-coder
```

Облачные и локальные модели обслуживает один класс `OpenAIClient`: все они
отдают `/v1/chat/completions` с одинаковым JSON, разница только в `base_url`.
SDK для этого не нужен — хватает одного POST через `httpx`, который уже стоит
как зависимость gigachat. `temperature=0`, чтобы прогон был воспроизводимым.

### Пополнить датасет

```bash
# мутационная генерация: ломаем чистый код и знаем эталон по построению
python -m scripts.mutate_t1 -o data/task1_lint/mutants.jsonl

# настоящие багфиксы из чужого репозитория (кандидаты, нужна ручная разметка)
python -m scripts.mine_git_fixes /path/to/repo -o data/task1_lint/mined.jsonl
```

**Мутационный генератор** (`scripts/mutate_t1.py`) — мутационное тестирование
наоборот: обычно мутанты проверяют тесты, здесь они проверяют модель. Берём
заведомо чистый сниппет, вносим ровно одну поломку известного типа — эталон
известен по построению (`error_type` = тип мутации, `fix` = исходная строка).
Каждый мутант верифицируется `compile()`: если обещанный `IndentationError` на
деле даёт `SyntaxError: 'return' outside function`, кейс отбрасывается — иначе
в датасет уехала бы неверная метка. На 7 донорах это отсеивает 4 из 11
кандидатов.

**Сбор из git-истории** (`scripts/mine_git_fixes.py`) — ищет коммиты с
fix/bug/patch в сообщении и берёт из них ханки ровно с одной удалённой и одной
добавленной строкой: формат ответа T1 — это одна строка `FIX:`, многострочный
рефакторинг в него не укладывается (он поедет в T3). Вместо построчного
`git blame` используется один `git log -p`: пары «до/после» он отдаёт сразу.
Тип ошибки из диффа не выводится, поэтому кандидаты помечены
`needs_review: true` и в `samples.jsonl` автоматически **не** попадают.

## T1 — ошибки статического анализа

Датасет `data/task1_lint/samples.jsonl`: 41 кейс — 33 базовых и 8
кейсов-ловушек (`metadata.difficulty`). Модель должна назвать тип ошибки и
дать исправленную строку (Exact Match + Classification Accuracy по заданию).

**Версия 2 — исправления по анализу провалов.** Анализ ответов GigaChat
(раздел «Анализ провалов» ниже) показал, что 11 из 12 провалов T1 были
дефектами самого бенчмарка, а не ошибками модели. Исправлено:

| Проблема в v1 | Что сделано в v2 |
|---|---|
| Модель не знала, из какого набора выбирать тип: писала `mutable-default-argument` вместо нашего `mutable-default` — верно по смыслу, но ноль по метрике | Тип выбирается из **закрытого списка** `ERROR_TYPES`, который есть в промпте. В список добавлены классы, которых нет в датасете (`KeyError`, `unused-variable` и др.), чтобы ответ нельзя было угадать перебором |
| Наши метки были выдуманными | Метки — **настоящие имена**: `mutable-default` → `dangerous-default-value`, `comparison-with-none` → `singleton-comparison` (так эти правила называются в pylint) |
| Метки проверялись глазами | `scripts/verify_t1_labels.py` проверяет **каждую** метку инструментом: синтаксические — `compile()`, ошибки выполнения — запуском кода, правила стиля — pylint, E501 — длиной строки. Все 41 метка подтверждены на Python 3.10, 3.12, 3.13 и 3.14 |
| Непонятно, как ответить «удалить строку»: на `unused-import` модель писала оставшуюся строку | В промпте: если строку нужно удалить, ответ `FIX: DELETE` |
| Парсер ломался, если модель давала фикс блоком кода на следующих строках: читал слово `python` вместо кода | Парсер понимает блок кода, буквальные `\n` и целый исправленный сниппет (берёт единственную изменённую строку) |

Чтобы после исправлений T1 не стал «всё 100%», добавлены **ловушки** —
кейсы, где очевидный ответ неверен:

| Кейс | Очевидный ответ | Правильный |
|---|---|---|
| `os.chmod("run.sh", 0755)` | обычное число | `SyntaxError` — восьмеричная запись Python 2, в Python 3 ведущие нули запрещены |
| таб среди пробелов в отступе | `IndentationError` | более конкретный `TabError` |
| `assert (x > 0, "msg")` | всё в порядке | `assert-on-tuple` — проверка всегда истинна |
| `role is "admin"` | всё в порядке, «иногда работает» | `literal-comparison` |
| `["id", "name" "email"]` | всё в порядке, код запускается | `implicit-str-concat` — пропущена запятая |
| `items[len(items)]` | — | `IndexError`, ошибка на единицу |
| `cfg.lr` у словаря | — | `AttributeError` (привычка из JavaScript) |
| метод без `self` | класс определяется без ошибок | `no-method-argument` |

**Метка может зависеть от версии Python.** Первая версия одной из
ловушек — `except ValueError, TypeError:` — была `SyntaxError` до Python 3.13,
но в Python 3.14 по PEP 758 такая запись стала допустимой. Это поймал тест
проверки меток на компьютере с Python 3.14. Ловушка заменена на устойчивую,
а все метки синтаксических ошибок и ошибок выполнения перепроверены в
контейнерах с Python 3.10, 3.12, 3.13 и 3.14.

В лидерборде колонка `Hard` — Pass только по ловушкам. Результаты v1 и v2
напрямую не сравнимы: изменились промпт, метки и состав кейсов.

## T2 — поиск уязвимостей

Датасет `data/task2_security/samples.jsonl`: 23 handcrafted-кейса на Python,
по доменам из задания — **Web** (12), **ML** (5), **System** (6). Классы
уязвимостей: SQL-инъекция (CWE-89), command injection (CWE-78), path
traversal (CWE-22), `eval` (CWE-95), небезопасная десериализация `pickle` /
`yaml` / `np.load` (CWE-502), `trust_remote_code` (CWE-94), захардкоженный
пароль (CWE-798), MD5 для паролей (CWE-916), предсказуемый токен (CWE-338),
open redirect (CWE-601), SSRF (CWE-918), пароль в логе (CWE-532), ReDoS
(CWE-1333), отключённая проверка TLS (CWE-295), TOCTOU (CWE-367), гонка на
общем счётчике (CWE-362), None-разыменование (CWE-476), `mktemp` (CWE-377),
права 0o777 (CWE-732).

Модель отвечает тремя строками — `LINES`, `CWE`, `CAUSE`. Строки сниппета в
промпте пронумерованы (`3| код`): проверяем умение найти баг, а не умение
считать строки.

| Метрика | Как считается |
|---|---|
| `line_precision` / `line_recall` / `line_f1` | пересечение названных строк с эталонными |
| `cwe_accuracy` | доля кейсов с верным CWE |
| `cwe_macro_f1` | F1 по каждому классу CWE отдельно, затем среднее без весов — редкие классы весят столько же, сколько частые |
| `pass_rate` | CWE верный, найдены **все** строки с багом и хотя бы половина названных строк — действительно баг |

Последнее условие не даёт «пройти» кейс, перечислив все строки подряд.

У одной уязвимости часто несколько корректных CWE: TOCTOU — это и CWE-367,
и родительский CWE-362; MD5 для паролей — CWE-916, CWE-328 или CWE-327.
Альтернативы перечислены в `metadata.acceptable_cwe` и засчитываются как
верный ответ — тот же принцип, что `multiple_valid` в T1.

Номера строк в эталоне не набирались руками: при составлении датасета
уязвимые строки помечались маркером, номера вычислялись по нему, а каждый
сниппет проверялся `compile()`. Валидатор дополнительно проверяет, что номер
строки существует в сниппете и что CWE записан в формате `CWE-<число>`.

## T3 — рефакторинг устаревшего кода

Датасет `data/task3_refactor/samples.jsonl`: 31 кейс на Python по доменам
**Web** (11), **ML** (11), **System** (9): 22 базовых и 9 кейсов-ловушек
(`metadata.difficulty`). Каждый кейс — функция в устаревшем стиле, её
современный эталон и unit-тесты. Паттерны: цикл с `append` →
list/dict comprehension, `range(len())` → `enumerate`/`zip`, склейка строк →
`str.join`, ручной подсчёт → `Counter`/`defaultdict`, ручной `max`/`sum`/флаг
→ `max`/`sum`/`any`/`all`, `try/finally` → `with`, `os.path` → `pathlib`,
вложенные `if` → одно условие, `keys()` + индекс → `items()`, `while` со
счётчиком → `range`, `map`/`filter` с `lambda` → comprehension,
шаблонный класс → `@dataclass`.

Проверка — как в задании: **unit-тесты**, и решение засчитывается, если
**тесты проходят, а количество строк / синтаксическая сложность снизились**.

| Шаг | Как |
|---|---|
| Функциональная идентичность | код модели + тесты кейса запускаются в Docker; тесты должны пройти |
| Количество строк (`loc`) | логические строки в `ast.unparse(кода)` — комментарии, пустые строки и переносы не влияют |
| Синтаксическая сложность (`ast_nodes`) | число узлов синтаксического дерева |
| Засчитан (`pass_rate`) | тесты прошли, ни `loc`, ни `ast_nodes` не выросли и хотя бы одно уменьшилось |

Докстринги из подсчёта исключены: модель не должна проигрывать за то, что
задокументировала функцию. В лидерборде `Tests` — доля кейсов с пройденными
тестами, `LOC↓` и `AST↓` — среднее относительное снижение по кейсам, где
тесты прошли (упростить код, сломав его, — не заслуга).

**Кейсы-ловушки (`hard`).** Базовые кейсы — классические паттерны,
которые современная модель знает наизусть. В кейсах-ловушках есть
«очевидный» рефакторинг, который выглядит правильно, но незаметно меняет
поведение, и тесты проверяют именно этот граничный случай:

| Кейс | Очевидный, но неверный рефакторинг | Что ломается |
|---|---|---|
| `latest_best` | `max(runs, key=...)` | при равных значениях исходник берёт последний элемент, `max` — первый |
| `unique_tags` | `list(set(tags))` | теряется порядок элементов |
| `sort_names` | `names.sort(key=str.lower)` | изменяется входной список |
| `first_error_line` | `next(генератор)` без default | `StopIteration`, если совпадений нет |
| `top_words` | `Counter.most_common(k)` | при равной частоте порядок появления вместо алфавитного |
| `format_address` | фильтр `if p` | выбрасывается и `0`, а не только `None` |
| `merge_config` | `defaults.update(overrides)` | портится словарь вызывающего |
| `pair_predictions` | `zip(preds, labels)` | разная длина обрезается молча вместо ошибки |
| `read_lines` | `line.strip()` | срезаются значимые пробелы |

Неверный вариант хранится в `metadata.naive_solution`, а описание ловушки —
в `metadata.trap`. Сборщик датасета и тест проверяют в Docker, что каждое
наивное решение **действительно проваливает** тесты, — иначе ловушка не
работала бы. В лидерборде колонка `Hard` — Pass только по этим кейсам.

**Docker-песочница** (раздел 3 задания: «каждая попытка генерации кода
запускается в изолированном контейнере»). Каждый ответ модели — одноразовый
контейнер `python:3.12-slim`: без сети (`--network none`), файловая система
только для чтения, пользователь `nobody`, без Linux capabilities, лимиты на
память, CPU и число процессов, таймаут. Код передаётся через stdin — папки
компьютера в контейнер не монтируются. Чтобы модель не могла «пройти»
тесты, завершив процесс раньше (`sys.exit(0)`), после тестов печатается
случайная метка, новая на каждый запуск; без неё кейс не засчитывается.
Тесты проверяют, что выход в сеть, запись в файловую систему, `sys.exit(0)`
и бесконечный цикл не засчитываются.

**Как собирался датасет.** Сборщик прогнал в Docker и исходник, и эталон
каждого кейса через его тесты и проверил, что эталон проще исходника. Один
кейс отсеялся: перевод `%`-форматирования на f-string — правильная
модернизация, но синтаксически f-string сложнее (18 узлов AST против 15).
Это ограничение правила «сложность снизилась» из задания: оно не видит
модернизацию, которая делает код читаемее, но не короче.

## Актуальные результаты

Прогон GigaChat-2-Pro на T1 v2 (41 кейс), T2 (23 кейса) и T3 (31 кейс),
см. `results/leaderboard.txt`, `results/run.json`, `results/predictions.jsonl`
и `results/error_analysis.md`. После прогона в парсере T1 нашлись ещё два
дефекта (см. «Что нашёл анализ провалов»); ответы модели после исправления
переоценены через `scripts/rescore.py` — модель заново не запускалась.

**T1 — ошибки статического анализа (v2):**

| Модель | EM | AST | Sim | TypeAcc | Hard | Pass | Задержка |
|---|---:|---:|---:|---:|---:|---:|---:|
| gigachat:GigaChat-2-Pro | **97.0%** | **90.0%** | **91.5%** | **82.9%** | **75.0%** | **82.9%** | ~1.5 с |
| noisy-baseline (p=0.5) | 57.6% | 53.7% | 62.2% | 61.0% | 62.5% | 51.2% | ~0 |
| noisy-baseline-weak (p=0.2) | 15.2% | 17.1% | 37.4% | 19.5% | 0% | 14.6% | ~0 |

По сравнению с v1 (Pass 63.6% на 33 кейсах) почти все ложные провалы
ушли, а провалы, которые остались, — настоящие (см. «Анализ провалов»).
Напрямую v1 и v2 не сравнимы: изменились промпт, метки и состав кейсов.

`echo-oracle` (верхняя граница, читает эталон из промпта) даёт 100% по всем
колонкам — sanity-check, что метрики вообще достижимы.

GigaChat строго обгоняет калиброванный baseline по всем метрикам —
стенд действительно измеряет качество.

**T2 — поиск уязвимостей:**

| Модель | LineP | LineR | LineF1 | CWE-Acc | CWE-F1 | Pass | Задержка |
|---|---:|---:|---:|---:|---:|---:|---:|
| gigachat:GigaChat-2-Pro | **91.3%** | **93.5%** | **91.3%** | **78.3%** | **67.9%** | **78.3%** | ~1.0 с |
| noisy-baseline (p=0.5) | 65.2% | 65.2% | 65.2% | 52.2% | 49.0% | 52.2% | ~0 |
| noisy-baseline-weak (p=0.2) | 52.2% | 52.2% | 52.2% | 30.4% | 26.5% | 30.4% | ~0 |

Строку с уязвимостью GigaChat находит уверенно (LineF1 91% против 65% у
baseline), а с классификацией по CWE справляется заметно хуже: CWE-Acc
78%, macro-F1 68%, и в разных прогонах macro-F1 менялся от 51.7% до 67.9%. Macro-F1
усредняет F1 по всем классам, включая те, что модель назвала ошибочно:
каждый неверный CWE, которого нет в эталоне, добавляет в среднее класс с
F1 = 0. Поэтому macro-F1 штрафует «разброс» ошибок сильнее, чем accuracy.
Вывод: найти опасную строку модели проще, чем точно назвать класс угрозы.
Анализ провалов показал, почему (см. ниже): модель понимает суть уязвимости,
но путает номер CWE.

**T3 — рефакторинг**, 31 кейс (`echo-oracle` в `run_demo` не входит и посчитан отдельно):

| Модель | Tests | LOC↓ | AST↓ | Hard | Pass | Задержка |
|---|---:|---:|---:|---:|---:|---:|
| gigachat:GigaChat-2-Pro | 90.3% | 48.4% | 34.8% | **66.7%** | **87.1%** | ~1.2 с |
| echo-oracle (эталон) | 100% | 60.2% | 43.6% | 100% | 100% | — |
| noisy-baseline (p=0.5) | 100% | 25.6% | 18.7% | 55.6% | 45.2% | ~0 |
| noisy-baseline-weak (p=0.2) | 100% | 5.9% | 2.3% | 11.1% | 9.7% | ~0 |

Шумная модель, когда «не справляется», возвращает исходный код без
изменений: тесты он проходит, но проще не стал — поэтому Tests = 100%, а
Pass заметно ниже. Именно это различие и ловит правило задания.

**Ловушки работают.** На 22 базовых кейсах GigaChat справился с 21
(95%) — классические паттерны модернизации современная модель знает, и
базовые кейсы почти не различают модели. На 9 кейсах-ловушках он прошёл
6 (**66.7%**; в одном из прогонов 5 из 9): в остальных применил
«очевидный» рефакторинг, который меняет поведение, или не стал
рефакторить вовсе. Итог по T3 — 27 из 31 (87.1%). Проваливаются одни и те
же кейсы от прогона к прогону — это систематические слабости, а не шум.

**Разброс между прогонами.** GigaChat отвечает от раза к разу немного
по-разному даже при `temperature=0`: на T1 v1 в разных прогонах Pass был
63.6% и 66.7% (разница в один кейс из 33), CWE macro-F1 на T2 — от 51.7%
до 67.9%. У baseline'ов seed
фиксирован, их цифры воспроизводятся до сотых. Поэтому для сравнения
моделей нужен bootstrap-анализ значимости (в roadmap).

**Ограничения Exact Match и multiple_valid.** У некоторых типов ошибок
допустимо несколько семантически эквивалентных фиксов: `bare-except`
можно закрыть любым классом исключения (`Exception`, `ValueError`,
`KeyError`), `E501` можно переносить строку разными способами,
`ZeroDivisionError` — защищать через `if`, `try` или тернарный оператор.
Для таких кейсов в `metadata` установлено `multiple_valid: true` —
evaluator не считает Exact Match, только Type Accuracy, и не наказывает
модель за форматирование.

**Мягкие метрики.** Exact Match снимает балл за лишний пробел или другие
кавычки, хотя фикс верный. Поэтому рядом с EM считаются ещё две метрики,
обе на стандартной библиотеке — новых зависимостей не появилось:

| Метрика | Как считается | Что ловит |
|---|---|---|
| `ast_match` | сравнение `ast.dump(ast.parse(fix))` обоих фиксов | семантическую эквивалентность: `if x==1 :` = `if x == 1:`, `"a"` = `'a'` |
| `fix_similarity` | `difflib.SequenceMatcher.ratio()` | насколько близок ответ, когда он не точен (роль CodeBLEU-lite) |

Строка фикса — это фрагмент, а не модуль, поэтому перед парсингом она
достраивается до валидного кода: как есть -> дописать тело (`if ...:` плюс
`pass`) -> обернуть в `try` (для `except ...:`). Если не распарсилось ни одним
способом, `ast_match` для кейса просто не считается — прогон не падает.

`pass_rate` теперь принимает и AST-совпадение, так что модель больше не
штрафуется за форматирование. Полноценный CodeBLEU и functional equivalence
через unit-тесты остаются в roadmap.

**Про калиброванные baseline'ы.** `noisy-baseline` — это не имитация
плохой нейросети, а честная лестница: с вероятностью `p_correct` модель
даёт правильный ответ (читая oracle-блок из промпта), иначе — случайный
из фиксированных списков. GigaChat oracle-блок **не получает**, оценивается
на чистом промпте: блок выдаётся только клиентам с `needs_oracle = True`, а в
базовом `LLMClient` этот флаг `False` — то есть любая новая реальная модель по
умолчанию подглядеть не может. Baseline'ы нужны, чтобы (а) убедиться, что стенд
чувствителен к качеству и (б) видеть, где реальная модель проседает
относительно контролируемого эталона.

## Анализ провалов (Error Analysis)

Раздел 5 задания требует выделить категории, на которых проваливаются
модели. Для этого `run_demo` кроме итоговых метрик сохраняет:

| Файл | Что внутри |
|---|---|
| `results/predictions.jsonl` | ответ каждой модели на каждый кейс: сырой ответ, распарсенный ответ, метрики, засчитан ли, домен / сложность / паттерн кейса |
| `results/error_analysis.md` | отчёт по провалам, собирается из `predictions.jsonl` автоматически |

Что показывает отчёт (по каждой реальной модели; baseline-заглушки не
включены, потому что они читают эталон из промпта):

- **T1** — Pass и угаданный тип по каждому типу ошибки, таблица проваленных
  кейсов: эталонный и предсказанный тип, эталонный и предложенный фикс;
- **T2** — результаты по доменам, **таблица путаницы CWE** (эталон, допустимые
  альтернативы, ответ модели) и кейсы, где строка с уязвимостью не найдена;
- **T3** — Pass на базовых кейсах и ловушках, причина каждого провала
  (тесты упали и каким исключением, код не стал проще — со строками и узлами
  AST до и после, код не парсится, ошибка запроса), а для ловушек — описание
  ловушки и код, который написала модель;
- **провалы всех моделей** — кейсы, которые не решила ни одна реальная
  модель, сгруппированные по типу ошибки / CWE / паттерну рефакторинга.

### Что нашёл анализ провалов

**Прогон v2.** В T1 после исправлений нашлись ещё два дефекта бенчмарка:
модель давала исправленный код на строках после `FIX:` без ```` ``` ````, а в
одном ответе сдвинула весь сниппет вправо — парсер не понимал ни то, ни
другое. Исправлено, ответы переоценены через `scripts/rescore.py`: T1 Pass
78.0% → 82.9%. Оставшиеся 7 провалов T1 — настоящие:

- **ошибки классификации (3):** для `'n=' + n` и `[1, 2] + (3, 4)` модель
  выбрала `implicit-str-concat` вместо `TypeError` — её сбило название из
  списка («склейка строк»); у `class Foo:` без отступа — `SyntaxError`
  вместо `IndentationError`;
- **ловушки (2):** табы среди пробелов назвала `IndentationError` вместо
  более конкретного `TabError`; пропущенную запятую в списке строк —
  `SyntaxError`, хотя код валиден;
- **ответ не по формату (2):** `unused-import: DELETE` одной строкой вместо
  `TYPE:` / `FIX:`. По сути верно, но не засчитано: следовать заданному
  формату — часть задачи. Такие ответы отчёт помечает отдельно.

В T2 и T3 провалы те же, что в v1: те же ошибки в номерах CWE и те же
4 кейса T3.

**Прогон v1.**

- **T1: большинство провалов — дефекты бенчмарка.** Из 12 проваленных
  кейсов 11 приходились на разные названия одного и того же типа ошибки,
  неописанный ответ «удалить строку» и сбой парсера на блоке кода.
  Реальная ошибка модели одна: у `class Foo:` без отступа она назвала
  `syntax-error` вместо `IndentationError`. Всё это исправлено в T1 v2.
- **T2: модель понимает уязвимость, но путает номер CWE.** В 4 из 6
  ошибок объяснение модели верное, а номер нет: гонку потоков («race
  condition, нет синхронизации») она пометила CWE-327 (криптография),
  `trust_remote_code` («выполнение чужого кода») — CWE-89 (SQL-инъекция).
- **T2 по доменам:** Web 92%, ML 60%, System 50%. Классические
  веб-уязвимости модель знает хорошо, ML-специфичные (`pickle`,
  `trust_remote_code`) и системные (гонки, TOCTOU) — заметно хуже.
- **T3: все провалы настоящие.** Модель попадала в ловушки (`max` при
  равенстве, `filter(None, ...)` выбрасывает `0`), однажды не стала
  рефакторить вовсе, а в одном базовом кейсе нашлась непреднамеренная
  ловушка: `sum(...)` без начального `0.0` возвращает `int` на пустом списке.

Отчёт можно пересобрать из сохранённых ответов без повторного прогона:

```bash
python -m scripts.error_analysis
```

Если поменялась сама оценка (парсер, метрика), сохранённые ответы можно
переоценить без новых запросов к модели — это обновит все файлы в `results/`:

```bash
python -m scripts.rescore
```

T1 и T2 оцениваются заново, T3 берётся из сохранённых результатов (код
модели от пересчёта не меняется). На ответах, которые изменение не
затрагивает, пересчёт даёт те же цифры — это проверено тестом.

## Тесты

```bash
python -m pytest tests/ -q
```

58 тестов. Базовые семь: загрузка датасета, работа парсера, EchoModel даёт
100% на oracle-промпте, NoisyModel всегда хуже эталона, лидерборд рендерится,
`case_id` уникальны, валидатор принимает актуальный датасет. Добавленные
восемь: `ast_match` прощает косметику но ловит неверный фикс, непарсящийся
ответ не роняет прогон, мутанты ломаются ровно так, как обещает метка, мутация
задевает ровно одну строку и fix восстанавливает донора байт в байт,
git-майнер берёт однострочные ханки и уважает фильтр расширений, список
моделей собирается из переменных окружения. Для T2 ещё восемь: датасет
проходит валидатор и покрывает три домена, валидатор ловит номер строки вне
сниппета, парсер понимает диапазоны `5-7` и запись `cwe 089`, промпт
нумерует строки и не содержит эталона, precision/recall и альтернативный CWE
считаются верно, macro-F1 сверен с ручным расчётом, echo даёт 100% а шум
меньше, лидерборд выводит отдельную таблицу на каждый таск. Для T3 ещё
тринадцать: датасет валиден и покрывает три домена, метрики сложности не
зависят от комментариев и докстрингов, правило «проще» работает на
граничных случаях, код извлекается из ответа, скорер засчитывает рабочий
упрощённый код и отклоняет неизменённый, сломанный и непарсящийся, команда
Docker содержит все ограничения и не монтирует папки хоста, каждый исходник
и эталон проходят тесты в настоящем контейнере, а сеть, запись в ФС,
`sys.exit(0)` и бесконечный цикл не засчитываются. Ещё три — про ловушки:
у каждого сложного кейса описаны ловушка и наивное решение, колонка `Hard`
считается только по ним, и каждое наивное решение реально проваливает тесты
в Docker. Тесты, которым нужен
Docker, пропускаются, если он не запущен. Для анализа провалов ещё четыре:
прогон сохраняет запись на каждую пару «модель × кейс», причины провала T3
определяются верно, отчёт не включает baseline-заглушки и перечисляет
проваленные кейсы, а в «провалы всех моделей» попадают только кейсы,
проваленные каждой моделью. Для T1 v2 ещё десять: промпт содержит список
типов с классами-дистракторами и `DELETE`, парсер правильно разбирает шесть
форматов ответа (блок кода, буквальные `\n`, `DELETE`, удаление блоком,
одиночная строка, backticks), у ловушек есть описание и колонка `Hard`,
синтаксические метки и ошибки выполнения подтверждаются `compile()` и
запуском, а правила стиля — pylint (тест пропускается, если pylint не
установлен). И ещё пять: парсер понимает код без ```` ``` ```` после `FIX:` и
сдвинутый вправо сниппет, ответ не по формату не засчитывается, а пересчёт
по сохранённым ответам воспроизводит метрики прогона.
